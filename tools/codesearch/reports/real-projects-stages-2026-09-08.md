# 真实项目搜索损失诊断

## 结论

本轮只增加同次调用诊断，不改变查询分析、模型输入、召回、融合、组装或 MCP 参数。
默认完整索引的 22 道已实现问题中，向量召回覆盖 18 道，最终只返回 8 道关键实现。
14 道失败里，10 道在召回之后丢失，4 道未进入召回集合。不能把所有失败归因于 Embedding 模型。

| 阶段 | 覆盖关键实现的题数 | 本阶段丢失 |
|---|---:|---:|
| 索引源码范围与向量缓存就绪 | 22/22 | 0 |
| 向量 Top-80 与全文 Top-50 的并集 | 18/22 | 4 |
| 融合、先验修正及候选 Top-40 | 14/22 | 4 |
| 扩展、合并及重新排序后 | 14/22 | 0 |
| 实际进入输出预算分配 | 10/22 | 4 |
| 正文裁剪后的最终返回 | 8/22 | 2 |

全文单路覆盖 10/22；本轮没有补回向量集合之外的已实现问题。覆盖只表示已有源码范围包含真值语句，
不是精确率，也不证明每个覆盖容器的 Embedding 表示都包含实现正文。

PHP 默认索引仍有 16 块未就绪，6 次诊断请求被评测器标为降级，不混入上表。
独立的 6000 字符输入上限补测索引完整：4 道已实现问题中，2 道未召回、1 道候选上限丢失、
1 道输出选择丢失，最终 0/4。完整问题与各阶段名次见[逐题表](real-projects-stages-v1-cases-2026-09-08.md)，
机器可读证据见[JSON](real-projects-stages-v1-2026-09-08.json)。

## 已确认的机制

### 1. 合并后按头部裁剪，删除原始命中

- `1167-2`，原始查询“按住说话时在哪里开始录音？”：`src/pages/index/index.vue:172-175`
  是向量第 1、全文第 1、融合第 1 的 4 行函数。组装把它合并为 66-175 行，仍排第 1，
  分配 590 个正文 token 后仅保留至 171 行，正好丢掉整个命中函数。扩展阶段并未改动该函数范围。
- `1491-4`，原始查询“语音输入的食材偏好如何识别并填回表单？”：
  `pages/meal/preference/preference.js:145-184` 的块被合并为 9-265 行，组装排第 3；
  分配 687 个正文 token 后只保留至 109 行，关键识别回填语句完全不可见。

因此“合并阶段没有减少覆盖题数”不等于合并没有问题。它把正确片段置于大段内容尾部，
随后固定头部裁剪造成损失。应保留原始命中范围作为预算锚点，而不是只增加输出长度。

### 2. RRF 与两级数量上限共同丢失候选

- `1507-5`，“子账号如何创建并关联到客户？”：真实方法为向量第 2，未进全文 Top-50，
  融合后第 19，组装后第 18，无法进入 10 项输出。融合前 16 项均同时命中全文与向量。
- `1167-5`，“切换聊天角色时如何更新当前身份？”：向量第 6，融合第 21，组装第 19。
- `1182-2`，“给员工安排一个服务任务时如何保存？”：向量第 12，融合第 26，组装第 22。
- `1507-3`，“订单发货时在哪里校验库存够不够？”：覆盖库存判断的最佳向量名次 53、全文名次 31，
  融合后最佳名次 60，被 40 块候选上限排除。返回的函数第一段 51-86 行本身未被正文裁剪；
  不能把这一题归为“库存比较被输出裁剪”。

两路默认权重均为 1、RRF k=60。双路尾部命中可得到 `1/110 + 1/140 = 0.016234`，
仍高于单路第 2 的 `1/62 = 0.016129`。这是实际排序机制，不意味着所有双路结果都无关。
应独立比较融合策略和有真实实现判断能力的重排；先将候选裁到 40 再重排，无法恢复已删除的答案。

### 3. 未召回与索引表示缺口

默认未召回的四题：酒店地区筛选、酒店发布提交、我发布的信息加载、境外仓入库更新库存。
对应目标块均已索引、向量缓存存在，关键语句完整保留在 Embedding 输入中；但不在本次向量 Top-80
或全文 Top-50。仅凭当前证据不能区分中文业务语境不足、向量相似度不足或近邻检索误差。
需要下一轮固定查询向量的全量余弦距离审计，先区分表示问题和 ANN 误差，再评估索引上下文或模型。

PHP 导出题额外暴露索引表示问题：`public/assets/js/require-table.js:16-20` 的关键配置只被
2-1071 行的概览块覆盖，没有独立正文块；概览的 `embed_input` 包含 `showExport: true`，
却不含完整的 `exportTypes` 配置。最终损失发生在召回，但这里不能说“实现正文已经完整向量化”。

## 修复顺序与验收

1. 先修复合并与裁剪的命中保留契约：完整短函数不得被邻接文本吞并，长片段的预算围绕命中范围分配。
   用录音和语音回填两题验证直接修复，同时回归全部真实问题及引用一致性；不能只让这两题通过。
2. 独立验证候选融合与重排：在同样的召回集合上比较，记录答案进入和离开 Top-40/Top-10 的原因。
   不把简单扩大结果数、按项目路径加权或硬编码业务词当成可靠性提升。
3. 对未召回题执行固定向量的全量距离审计，再决定补业务上下文、修复正文切块或比较 Embedding 模型。
   单独修复 PHP 长输入失败和概览遗漏；索引就绪状态不能掩盖正文表示缺失。
4. 每次只改一个变量，保留当前问题作回归；增加未参与调优的真实项目盲测，报告实现 Top-1/5/10、
   配对胜负、失败记录、索引完整率及延迟。没有盲测证据前不得宣称“闭眼信”。

## 复现

在 `tools/codesearch` 执行，需环境变量 `SILICONFLOW_API_KEY`；先建立上一份报告记录的索引。
不要复用已有输出标签，否则诊断程序拒绝覆盖原始证据。

```sh
bun eval/diagnose_real_projects.ts --preflight
cargo build --all-features
cargo run --example real_projects -- --diagnostic-binary /绝对路径/codesearch --label 新标签
cargo run --example real_projects -- --diagnostic-binary /绝对路径/codesearch --label 新标签 --supplement-php
bun eval/diagnose_real_projects.ts --label=新标签 --binary=/绝对路径/冻结构建
```

本次版本化逐题表与 JSON 由 `bun eval/diagnose_real_projects.ts --publish` 生成。
