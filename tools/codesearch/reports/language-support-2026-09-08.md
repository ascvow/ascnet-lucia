# 语言扩展与语义定位评测

结论：结构化支持与协议闭环已验证，受控样本的定位命中率提高；**仍未达到“闭眼信”的通用可靠性目标**。
真实查询仍有漏召回、个别名次回退和尾延迟波动，不能把下面的小样本结果外推为任意仓库的准确率。

## 变更范围

- 新增 Dart/Flutter、Elixir、Zig、Haskell、HCL/Terraform、GraphQL 的语法解析、定义提取、文件识别与语言过滤。
- HTML 内嵌脚本与样式进入结构化解析；Vue/Svelte 改用 HTML 语法识别元素，修复注释伪脚本、带 `>` 的属性、`data-lang` 干扰、JSON 数据脚本及外部脚本误识别。
- Vue `defineComponent` 与 Pinia `defineStore` 提取静态选项对象方法；不会递归猜测任意业务调用。
- Haskell 同名类型签名、文档与实现共同成块；Go 方法限定名包含接收者，但不伪造源码包含关系。
- Elixir/Ruby 的 `?`、`!` 符号后缀不再被查询清洗丢弃；普通多词问句仍沿用原有标点处理。
- MCP 新增 `search_context`，保留 `search_code` 兼容入口，共用同一引擎和返回契约；读取继续使用 `read_code`。
- `CHUNKER_VERSION` 从 1 升到 2，让已有未修改文件也能在下次索引时采用新分块。未修改融合权重、向量模型、候选预算与上下文预算默认值。

现有 33 类语言/格式中，28 类有结构化入口。结构化入口不等于完整语言服务器：
模板绑定、宏展开、复杂 CSS 预处理器、跨文件类型解析与调用图仍不在本次支持范围内。
框架 fixture 用于验证源码语法与搜索，不是安装了完整依赖的可运行业务服务。

## 评测方法

基线是在本次改动前、`tools/codesearch` 干净状态下由 `c71846d` 构建并保留的二进制。
候选使用最终实现的冻结二进制。每组让两个二进制索引同一份语料，使用独立数据目录，
模型均为 SiliconFlow `BAAI/bge-m3`、1024 维，配置见 `eval/semantic.toml`。凭证只来自环境变量。

三组各 20 条查询，每个版本每条执行 3 次，最终一轮实验共 **360 次真实模型搜索**：

1. 中文多语言定位：16 个文件，要求期望路径与指定实现片段同时命中，且片段位于返回行范围内。
2. 英文留出查询：同一批文件的另一组英文表达，用于检查跨语言语义迁移。它是查询留出，不是独立仓库留出；与中文组有相关性，不能合并冒充 40 个独立场景。
3. 工具自身真实源码：84 个文件，沿用原有 `eval/queries.json` 的路径真值。包含自然语言、符号、路径和字面量；这组是文件级指标，不能与前两组的实现片段级指标混为一谈。

查询集和报告从搜索作用域排除。每次最多返回 10 项、预算 16000 估算 token，两侧相同；
没有按预期语言或预期文件过滤来降低任务难度。该预算不是生产默认预算，结果不能直接外推到默认配置。
索引的 pending/failed 均为 0，查询全部实际使用向量召回且没有降级；服务失败不会计为成功或悄悄回退。

下表的 Top-K 是“前 K 项至少命中一个有效答案的查询比例”，对应评测 JSON 的 `recall*` 字段。
名次与 MRR 采用每条首轮观测，重复轮次只用于检查稳定性与延迟，不能当作额外独立样本。

| --- | --- | --- | --- | --- |
| 中文多语言 | 50% → 80% | 85% → 90% | 85% → 95% | 0.6792 → 0.8433 |
| 英文留出 | 45% → 60% | 80% → 95% | 85% → 95% | 0.6238 → 0.7500 |

双侧配对符号检验：中文 7 升、2 降，p=0.1796875；英文 6 升、1 降，p=0.125；

中文与英文名次在三轮中一致；工具自身“驼峰和下划线拆词”基线首轮第 8、随后两轮第 9，候选均第 9。

## 未命中与回退

- 中文“高并发访问时怎样原子减少剩余请求次数”：基线实现第 8，候选实现不在 Top-10。
  两侧 Top-1 都是 `server/limiter.go:5-9` 的类型说明，真正实现位于 11-17 行；**文件对了不计实现命中**。
  英文对应问题两侧实现都不在 Top-10。本次方法身份修复并没有解决这一语义上下文问题。
- 中文 GraphQL 游标翻页：实现第 3 → 第 5；候选 Top-1 是相关类型定义，不是查询操作实现。
- 英文 Flutter 金额显示：第 1 → 第 2。其他英文查询的提升不能抵消这个单条回退事实。
- 工具自身“文件保存后多久会被重新索引”：两侧都未命中标注实现路径。
- 工具自身的拆词、超时重试配置查询仍在 Top-5 之外。因此没有通过“所有语义提问都直接定位到实现”的验收。

以上只定位到最终输出的丢失，未增加同调用的各召回阶段诊断，不能据此声称一定是向量、融合或上下文某一阶段的单独原因。
下一阶段应基于这些固定失败样本补充同调用阶段证据，并增加未参与开发的真实多语言仓库真值集，
再分别验证召回与上下文策略；不应通过添加查询词表或只展示成功案例来提高表面指标。

## 延迟结果

| 查询组 | 中位数 基线 → 候选 | P95 基线 → 候选 |
| --- | --- | --- |
| 中文多语言 | 305.5 → 304.0 | 417.9 → 737.2 |
| 英文留出 | 308.7 → 305.3 | 394.7 → 1364.8 |
| 工具自身 | 315.7 → 319.3 | 427.8 → 467.8 |

最终运行中三组任务和模型 smoke test 有重叠，远程服务与本机资源并未独占。
所以这些是真实交互延迟记录，不是隔离环境下的解析器性能基准，也不能据此证明波动全由模型或代码造成。
**候选的尾延迟未达到稳定无回退的要求**，没有选择之前较快的一轮替换最终结果。

## 复现与证据

在 `tools/codesearch` 下，已保留的基线和候选二进制分别为
`target/codesearch-baseline`、`target/codesearch-candidate-final`。示例：

```bash
bun eval/run_ab.ts \
  --baseline target/codesearch-baseline \
  --candidate target/codesearch-candidate-final \
  --root tests/fixtures/multilingual \
  --queries eval/multilingual.json \
  --config eval/semantic.toml \
  --out target/eval-multilingual-final --rounds 3
```

英文组换用 `eval/multilingual-holdout.json` 和独立 `--out`；自身回归用 `--root . --queries eval/queries.json`。
需要配置 `SILICONFLOW_API_KEY`，也可显式换用另一份 Provider 配置，但不同模型结果不能直接拼接比较。
源码语料变化、解析器变化或从头构建基线时应使用新的输出目录，避免复用不匹配的实验索引。

[机器可读摘要](language-support-2026-09-08.json) 保留每条查询三轮名次、延迟、首项与命中行范围，
以及二进制、查询集和配置的 SHA-256。完整原始结果和索引位于
`target/eval-multilingual-final/`、`target/eval-holdout-final/`、`target/eval-self-final/`。
