## 实际调用方式

使用冻结的 `1989253` 实现，通过官方 `rmcp` 客户端启动真实 stdio 服务，每条实际发送：

```json
{"name":"search_context","arguments":{"query":"订单发货时在哪里校验库存够不够？"}}
```

没有传 `include`、`exclude`、`language`、`max_results` 或 `token_budget`。
搜索保持默认最多 10 项、6000 估算 token；模型为 SiliconFlow `BAAI/bge-m3`、1024 维。
每条执行 3 轮，准确率只用首轮，重复轮次不增加独立样本数。
默认阶段共 108 次请求，另有 PHP 输入上限补测 18 次、1507 源码版本重测 18 次；成绩不合并重复请求充当新问题。

对非降级结果逐项调用 `read_code`，校验内容哈希、磁盘源码、行范围和搜索片段包含关系。
索引完整的默认组校验 900 个引用，PHP 补测校验 180 个引用，均通过同版本原文验证。
搜索可按字节边界从行中开始，`read_code` 按整行读取；多出首尾行的邻接字符是合法情况，不应误报内容损坏。
首个探测器误用了逐字相等判定，已纠正并完整重跑；旧探测记录保留，但不计入下述成绩。

## PHP 索引失败与独立补测

默认模型输入上限为 16000 字符。`addons/epay/view/index/index.html:17` 对应输入长 14660 字符，
单独调用模型返回 HTTP 400；相同输入取前 6000 字符时返回 HTTP 200、1024 维向量。
这说明存在该输入与服务的兼容性问题；服务只给出通用参数错误，不能据此推导一个精确 tokenizer 上限。

原始批次有 16 个块连带失败，不能把其余块成功当作整个索引成功。默认 MCP 查询明确处于降级状态，故不进入主准确率。
后续打开服务时这些块转回 pending，原始索引仍不完整；初始失败和最终状态分别保存。

补测只把 PHP 配置的 `embedding.max_input_chars` 改为 6000，使用独立配置、独立索引，不改原项目源码或检索参数。
8567 个块最终全部就绪，但 4 条已确认实现问题的文件和关键实现 Top-10 仍为 **0/4**。
例如新增、审核和表格导出问题，Top-1 都被工单语言包占据，未返回预标注的真实处理位置。
补测中位查询耗时 161.8ms、P95 247.4ms；不会把这个配置调整后的结果混入默认配置指标。
