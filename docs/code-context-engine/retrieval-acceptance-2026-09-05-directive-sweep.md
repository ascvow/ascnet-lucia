# 中文指令词剥离的跨仓库高样本验收

日期：2026-09-05。被测提交 `97f8614`，对照为同一提交上还原三处修复后的构建（还原点：
`search_execution` 里的 `resolve_leading_directive` 调用、重排使用的查询文本、
`is_substantive_block` 过滤）。两个构建除此之外完全一致，因此差异只归因于这三处改动。

语料为 `~/WebstormProjects` 下的真实业务仓库，绝大多数是 uni-app / Vue 前端。这些仓库不在
本工程内，可避免"用代码检索工具检索自己"带来的自指偏差。

**注意分支**：`915_frontend` 的工作副本检出在 `chore/remove-live-code` 上，直播代码已被删除。
第一、二节的扫描跑在该副本上；第四节改用只读导出的 `origin/main`（记为 `915_main`），直播与
开播代码完整存在。跨节比较 915 的结果时必须区分这两者。

## 查询集

24 条查询，模仿实际使用时的写法——中文、开头带指令动词、不含目标符号名：

- 20 条**指令式**：`搜索登录代码`、`搜索支付逻辑`、`搜索主播开播代码` 等，覆盖登录、支付、
  订单、上传、分页、定位、扫码、推送、购物车、路由拦截、请求封装等常见前端业务。
- 4 条**复合词陷阱**：`搜索结果怎么展示`、`查询订单接口在哪`、`定位服务怎么初始化`、
  `检索历史记录怎么存`。开头那个词在这些查询里是主题的一部分，剥离即为错误。

每条查询同时跑一个**对照变体**：人工去掉开头指令词后的文本（`搜索登录代码` → `登录代码`）。
两次检索结果的差异，就是指令词造成的偏移量——无需人工标注答案即可量化。

> **这组一致性指标不能当作质量证据。** 修复之后引擎本来就用剥离后的文本去检索，与对照一致
> 是必然的，指标只证明代码按设计执行了。真正的质量结论见「四、带客观真值的质量评测」。

## 判定真值

剥离决策的真值是 **仓库源码里是否真的出现过该复合词**（`rg` 字面量检索）：出现过，说明它是
主题，应保留；从未出现过，说明它是指令，应剥离。这与实现使用的判据（跨界 bigram 的文档
频次）不是同一个量，因此构成独立校验。

无重排，完全离线可复现。

## 二、真实链路扫描

5 个仓库 × 24 查询 × 2 变体 × 2 构建 = **120 条样本 / 构建**。真实 `BAAI/bge-m3`（1024 维）
语义召回与 `Qwen/Qwen3-Reranker-4B` 重排，与日常使用的配置一致。

| 指标 | 改动前 | 改动后 |
| --- | --- | --- |
| 剥离判定与语料真值一致 | 7/120（5.8%） | 118/120（98.3%） |
| 误剥真复合词 | 0 | 0 |
| 与去指令词对照的 Top-1 一致 | 53/120（44.2%） | 111/120（92.5%） |
| 与去指令词对照的 Top-5 重合 | 37.9% | 90.2% |

| ≤3 行的极短结果占比 | 16.8% | 9.8% |

真实链路的偏移量比离线更大（改动前 55.8% 的查询 Top-1 被指令词带偏，离线为 36.3%），与
最初定位一致：污染主要发生在语义通道，指令动词直接进入了嵌入请求。

纯文本块占比只能在**对照口径**下比较：原查询在两个构建里已经不是同一段文本，把它的变化算作
碎片过滤的效果是错的。对照变体两侧输入完全相同，29.7% 对 34.7% 才是碎片过滤的真实贡献；
离线口径下同一指标为 11.4% → 11.5%，即碎片过滤对离线路径几乎无效。

## 四、带客观真值的质量评测

一致性指标测不出质量，因此另建一套有正确答案的评测。**真值不靠人工标注，也不含任何项目
专属规则**：先用正则从仓库源码抽出全部函数名（915_main 抽出 3483 个），再用一张通用的
「中文业务词 → 英文标识符词」表（`登录→login|signin|auth`、`开播→openlive|startlive|
livepush|pusher|anchor|liveroom` 等 24 组）判定两件事——该查询在这个仓库有没有答案，以及
返回的某条结果算不算命中。

命中判据是**符号名的驼峰/下划线分词等值**，长复合词才允许整体子串匹配。因此 `displayText`
不会被算成 `play`、`designMode` 不会被算成 `sign`、`getPages` 不会被算成 `page`。纯文本块没有
符号名，一律不算命中。仓库里不存在该领域任何函数时，这条查询不计入分母。

7 个仓库（915 的 `main` 分支 + 6 个业务前端）共 **113 条有答案的查询**：

| 指标 | 改动前 | 改动后 | 差 |
| --- | --- | --- | --- |
| Precision@1 | 58.4% | 61.9% | +3.5 |
| Precision@3 | 42.2% | 46.3% | +4.1 |
| Precision@5 | 35.0% | 37.7% | +2.7 |
| Precision@10 | 25.0% | 28.5% | +3.5 |
| Top-10 文本块占比 | 35.3% | 28.7% | −6.6 |
| Recall@1 | 58.4% | 61.9% | +3.5 |
| Recall@3 | 69.0% | 67.3% | −1.8 |
| Recall@10 | 78.8% | 78.8% | ±0.0 |
| MRR | 64.6% | 66.5% | +1.9 |

**结论：准确率提升、召回持平。** 逐查询配对符号检验，Precision@10 改善 35 条、变差 10 条，
单尾 p = 0.0001，显著。名次本身的变化（变好 11、变差 8、持平 94）p = 0.324，不显著——这次
改动让返回列表更干净，但没有让正确答案排得更靠前。

### 两处修复各自的贡献

把已剥离的文本同时喂给两个构建，查询完全相同，差异只可能来自分块改动，据此拆解：

| 来源 | Precision@10 | Top-10 文本块占比 |
| --- | --- | --- |
| 合计 | +3.5 | −6.6 |
| 其中：指令词剥离 | +2.9 | +1.1 |
| 其中：碎片块过滤 | +0.5 | −7.7 |

指令词剥离贡献了绝大部分准确率提升；碎片块过滤准确率增益很小，但独自清掉了 7.7 个百分点
的无符号文本块。此前根据 `915_main` 单条查询得出的「碎片过滤弊大于利」判断是错的——那条
查询上它恰好中性，113 条上它是正向的。

**口径偏袒说明**：文本块永远不算命中，这条规则天然对碎片过滤有利。但它实际只换来 +0.5 个
百分点，说明顶替上来的多数并非领域内符号；它的价值主要在于把无符号可跳转的块换成具名结果。

## 五、遗留问题

1. **11 条漏剥**（占 0.9%）。跨界 bigram 在大语料里偶然出现过，判据便退回保留。这是阈值取 0
   的已知代价，失败方向是"退回改动前的行为"，不会误伤。样例：`915_frontend` 的
   `搜索图片上传实现`、`1260_frontend` 的 `搜索地图定位代码`。
2. **正确答案没有排得更靠前**。名次变化不显著（p = 0.324），本次改动只让列表更干净，没有提升
   定位能力。要提升名次需要动召回或重排本身，不是清理查询文本能解决的。
3. **极短结果仍占 Top-1 的 9.2%**（真实链路）。`is_substantive_block` 只丢弃"整块都是注释"的
   间隙块，一行 `const x = ref(0)` 含字母数字，仍被判为有实质内容。若要继续压，需要给 Vue
   声明间隙块加最小行数门槛，而不只看是否为注释。
4. **非源码文件占 5.3%**（离线）。`.md`、`.scss`、`.html`、`changelog.md`、`readme.md` 会作为
   Tier-3 全文件文本块进入结果。指令词剥离后查询更偏中文业务词，这类文件反而更容易命中，
   占比从 2.4% 升到 5.3%。

## 复现

```sh
# 构建对照：在同一提交上还原三处修复后单独 build
# 两个构建分别喂入同一批查询，逐仓库一次建索引、连续查询
printf '%s\n' "${QUERIES[@]}" | ./search_playground --root <仓库> --diagnostics --limit 5
```

`--diagnostics` 输出的 `检索文本  X（已剥离开头指令词）` 一行即为剥离判定的观测点；未打印
该行表示保留了原查询。真实链路需配置 `SILICONFLOW_API_KEY`，并复用 `~/.lucia/code-context/`
下的按仓库向量缓存，否则每轮都会重新嵌入全仓库。

指标为本机与当次端点的结果，不作为跨环境 SLA；查询集偏向 uni-app 业务前端，不能代表后端或
其他技术栈的检索准确率。
