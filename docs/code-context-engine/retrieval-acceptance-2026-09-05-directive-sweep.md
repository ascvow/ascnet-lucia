# 中文指令词剥离的跨仓库高样本验收

日期：2026-09-05。被测提交 `97f8614`，对照为同一提交上还原三处修复后的构建（还原点：
`search_execution` 里的 `resolve_leading_directive` 调用、重排使用的查询文本、
`is_substantive_block` 过滤）。两个构建除此之外完全一致，因此差异只归因于这三处改动。

语料为 `~/WebstormProjects` 下的真实业务仓库，绝大多数是 uni-app / Vue 前端。这些仓库不在
本工程内，可避免"用代码检索工具检索自己"带来的自指偏差。

**注意分支**：`915_frontend` 的工作副本检出在 `chore/remove-live-code` 上，直播代码已被删除。
第一、二节的扫描跑在该副本上；第四节改用只读导出的 `origin/main`（记为 `915_main`），直播与
开播代码完整存在。跨节比较 915 的结果时必须区分这两者。

## 查询集

24 条查询，模仿实际使用时的写法——中文、开头带指令动词、不含目标符号名：

- 20 条**指令式**：`搜索登录代码`、`搜索支付逻辑`、`搜索主播开播代码` 等，覆盖登录、支付、
  订单、上传、分页、定位、扫码、推送、购物车、路由拦截、请求封装等常见前端业务。
- 4 条**复合词陷阱**：`搜索结果怎么展示`、`查询订单接口在哪`、`定位服务怎么初始化`、
  `检索历史记录怎么存`。开头那个词在这些查询里是主题的一部分，剥离即为错误。

每条查询同时跑一个**对照变体**：人工去掉开头指令词后的文本（`搜索登录代码` → `登录代码`）。
两次检索结果的差异，就是指令词造成的偏移量——无需人工标注答案即可量化。

> **这组一致性指标不能当作质量证据。** 修复之后引擎本来就用剥离后的文本去检索，与对照一致
> 是必然的，指标只证明代码按设计执行了。真正的质量结论见「四、带客观真值的质量评测」。

## 判定真值

剥离决策的真值是 **仓库源码里是否真的出现过该复合词**（`rg` 字面量检索）：出现过，说明它是
主题，应保留；从未出现过，说明它是指令，应剥离。这与实现使用的判据（跨界 bigram 的文档
频次）不是同一个量，因此构成独立校验。

## 四、带客观真值的质量评测

一致性指标测不出质量，因此另建一套有正确答案的评测。**真值不靠人工标注，也不含任何项目
专属规则**：先用正则从仓库源码抽出全部函数名（915_main 抽出 3483 个），再用一张通用的
「中文业务词 → 英文标识符词」表（`登录→login|signin|auth`、`开播→openlive|startlive|
livepush|pusher|anchor|liveroom` 等 24 组）判定两件事——该查询在这个仓库有没有答案，以及
返回的某条结果算不算命中。

命中判据是**符号名的驼峰/下划线分词等值**，长复合词才允许整体子串匹配。因此 `displayText`
不会被算成 `play`、`designMode` 不会被算成 `sign`、`getPages` 不会被算成 `page`。纯文本块没有
符号名，一律不算命中。仓库里不存在该领域任何函数时，这条查询不计入分母。

7 个仓库（915 的 `main` 分支 + 6 个业务前端）共 **113 条有答案的查询**：

| 指标 | 改动前 | 改动后 | 差 |
| --- | --- | --- | --- |
| Precision@1 | 58.4% | 61.9% | +3.5 |
| Precision@3 | 42.2% | 46.3% | +4.1 |
| Precision@5 | 35.0% | 37.7% | +2.7 |
| Precision@10 | 25.0% | 28.5% | +3.5 |
| Top-10 文本块占比 | 35.3% | 28.7% | −6.6 |
| Recall@1 | 58.4% | 61.9% | +3.5 |
| Recall@3 | 69.0% | 67.3% | −1.8 |
| Recall@10 | 78.8% | 78.8% | ±0.0 |
| MRR | 64.6% | 66.5% | +1.9 |

**结论：准确率提升、召回持平。** 逐查询配对符号检验，Precision@10 改善 35 条、变差 10 条，
单尾 p = 0.0001，显著。名次本身的变化（变好 11、变差 8、持平 94）p = 0.324，不显著——这次
改动让返回列表更干净，但没有让正确答案排得更靠前。

### 两处修复各自的贡献

把已剥离的文本同时喂给两个构建，查询完全相同，差异只可能来自分块改动，据此拆解：

| 来源 | Precision@10 | Top-10 文本块占比 |
| --- | --- | --- |
| 合计 | +3.5 | −6.6 |
| 其中：指令词剥离 | +2.9 | +1.1 |
| 其中：碎片块过滤 | +0.5 | −7.7 |

指令词剥离贡献了绝大部分准确率提升；碎片块过滤准确率增益很小，但独自清掉了 7.7 个百分点
的无符号文本块。此前根据 `915_main` 单条查询得出的「碎片过滤弊大于利」判断是错的——那条
查询上它恰好中性，113 条上它是正向的。

**口径偏袒说明**：文本块永远不算命中，这条规则天然对碎片过滤有利。但它实际只换来 +0.5 个
百分点，说明顶替上来的多数并非领域内符号；它的价值主要在于把无符号可跳转的块换成具名结果。

## 五、后续优化：两个方案，一成一败

沿用第四节那套真值评测（同一批 113 条查询、同一套判据）验证了两个方向。

### 失败：伪相关反馈（PRF / RM3）

思路来自经典 IR：把首轮结果当作伪相关样本，按 `Σ(词频/文档长度) × idf` 提取区分度最高的
词元，再做一次词法召回，作为第四路参与 RRF。动机是诊断里那组数字——中文查询的三路召回
是「符号 0 · 词法 24 · 语义 120」，词面两路形同虚设，PRF 能把语义通道找到的英文标识符带回
词法空间。

实现中先撞上一个必须处理的坑：反馈通道与词法通道用的是同一套 BM25，命中高度相关，同时
进入 RRF 就是把同一份词面证据数两遍。实测 `索引 manifest 持久化` 因此把 `storage.rs` 整体挤
出前 20，顶上来的全是 `feedback#N + lexical#N` 的双计分候选。去掉与词法通道重叠的候选后
回归测试恢复通过。

但真值评测显示它没有价值：

| 指标 | 无反馈 | 有反馈 |
| --- | --- | --- |
| Precision@1 | 62.8% | 61.1% |
| MRR | 66.9% | 65.9% |
| Recall@10 | 78.8% | 77.9% |

名次变好 2 条、变差 5 条（p = 0.938）。**已回退，代码未合入。**

### 成功：扩大模型重排候选池

依据是 Anthropic 关于 Contextual Retrieval 的工程说明——先召回一两百条再交给重排模型。本地
融合在中文查询上排不准，它能保证的只是"正确答案落在候选池里"，真正做判别的是交叉编码器，
因此瓶颈在池深而不在本地排序。候选池上限从 40/48 提到 150，自然语言查询的池下限从 40 提到
120。

| 指标 | 池=40（原） | 池=80 | 池=150 |
| --- | --- | --- | --- |
| Recall@1 | 62.8% | 63.7% | 63.7% |
| Recall@3 | 67.3% | 69.0% | **73.5%** |
| Recall@5 | 72.6% | 75.2% | **77.0%** |
| Recall@10 | 78.8% | 79.6% | **82.3%** |
| MRR | 66.9% | 68.1% | **69.7%** |
| Precision@3 | 46.0% | 47.8% | **50.4%** |
| Precision@10 | 28.6% | 29.6% | **30.1%** |

池=150 相对原状态：名次变好 12 条、变差 5 条（p = 0.072）；Precision@10 逐查询改善 26 条、
变差 11 条（**p = 0.010，显著**）。池=80 只拿到约四分之一的收益，不值得为折中牺牲准确率。

这是第一个真正改善**名次**的改动——此前指令词剥离只提升准确率，Recall@3 反而略降。

**延迟代价**：915_main 上六条查询的中位耗时约 1.9–3.0 秒涨到约 4.7 秒。重排请求体随候选数近似
线性增长，端点抖动使同一档两次测量差到 1 秒以上，因此这些数字只表明量级。

### 中性但保留：重排后恢复角色与体量降权

融合层有文档、配置、类型定义、短块四类降权，但自然语言查询的重排会用模型相关度**直接替换**
本地分数，这四项随之消失，原实现只单独保留了测试降权。实测查 `用户开播代码` 时，一份说明
如何删除直播代码的 Markdown 拿到 0.82 的模型相关度排在第一——它确实语义相关，但用户要的是
代码。已抽出 `role_size_weight` 供融合与重排共用，该查询上两份 Markdown 从 #1/#2 降到 #4/#5。

90 条真值查询上的 A/B 是**中性**的（名次变好 1、变差 1、持平 88；Precision@10 逐查询改善 4、
变差 0）。这批 uni-app 前端几乎没有 Markdown 文档，触发不了该路径。保留的理由是它补的是确定
的逻辑漏洞而非调参，且从未观察到劣化。

## 六、真值审计与失败归因

### 判据里的假朋友

复合领域词此前按"出现在符号名里的任意子串"匹配，会把 `preview` 判成 `review`、把
`textObjectCollection` 判成 `collect`。已改为要求**由连续分词拼接**而成：`openlive` 仍能
匹配 `indexOpenLive`（open + live），`review` 不再匹配 `preview`。

规则修好后仍有一批语义假朋友，只能人工审计：

| 领域词 | 在前端仓库里实际指什么 | 影响 |
| --- | --- | --- |
| `anchor` | **锚点定位**，不是主播 | `搜索主播开播代码` 假失败 1 条 |
| `address` | 命中的全是 `isValidIpAddress` 等 **IP 地址校验** | `搜索收货地址代码` 假失败 5 条 |
| `comment` / `review` | 裸变量 `comment`、`approvalComment`（审批意见） | `搜索评论列表代码` 假失败 6 条 |

89 条里有 13 条根本不存在正确答案，却被计入了分母。

### 修正后的质量

| 指标 | 机械口径（89 条） | 人工审计后（76 条） |
| --- | --- | --- |
| Recall@1 | 67.4% | **78.9%** |
| Recall@3 | 70.8% | **82.9%** |
| Recall@5 | 75.3% | **88.2%** |
| Recall@10 | 82.0% | **93.4%** |
| MRR | 70.9% | **82.6%** |

此前各节报告的绝对数值都偏低，原因即此。A/B 结论不受影响——同一判据施加于两侧。

### 失败归因：瓶颈在召回，不在排序

取 50 条结果看目标落点（90 条查询）：

| 名次段 | 占比 |
| --- | --- |
| 第 1 名 | 64.4% |
| 第 2–3 名 | 5.6% |
| 第 4–10 名 | 12.2% |
| 第 11–50 名 | 2.2% |
| 50 条内完全没有 | 15.6% |

Top-10 未命中中，**88% 是目标压根没进 50 条**，只有 12% 是"召回到了排不上去"。继续扩大候选池
或调整排序对前者无效，必须动召回本身（嵌入质量、查询改写、索引内容）。

审计后剩余 5 条真实未命中：`1063 视频播放`、`1270/1220 分页加载`、`1131 分享功能`、
`1220 签到功能`。共同点是目标符号纯英文命名且与中文查询词无字面关联
（`handleAttendanceClick` 对"签到"、`jumpToShare` 对"分享"），只能靠语义通道，而语义没召回。

## 七、遗留问题

1. **11 条漏剥**（占 0.9%）。跨界 bigram 在大语料里偶然出现过，判据便退回保留。这是阈值取 0
   的已知代价，失败方向是"退回改动前的行为"，不会误伤。样例：`915_frontend` 的
   `搜索图片上传实现`、`1260_frontend` 的 `搜索地图定位代码`。
2. ~~**正确答案没有排得更靠前**~~。已由第五节的候选池扩大解决：Recall@3 从 67.3% 升到
   73.5%，MRR 从 66.9% 升到 69.7%。
3. **极短结果仍占 Top-1 的 9.2%**（真实链路）。`is_substantive_block` 只丢弃"整块都是注释"的
   间隙块，一行 `const x = ref(0)` 含字母数字，仍被判为有实质内容。若要继续压，需要给 Vue
   声明间隙块加最小行数门槛，而不只看是否为注释。
4. **非源码文件占 5.3%**（离线）。`.md`、`.scss`、`.html`、`changelog.md`、`readme.md` 会作为
   Tier-3 全文件文本块进入结果。指令词剥离后查询更偏中文业务词，这类文件反而更容易命中，
   占比从 2.4% 升到 5.3%。

## 复现

```sh
# 构建对照：在同一提交上还原三处修复后单独 build
# 两个构建分别喂入同一批查询，逐仓库一次建索引、连续查询
printf '%s\n' "${QUERIES[@]}" | ./search_playground --root <仓库> --diagnostics --limit 5
```

`--diagnostics` 输出的 `检索文本  X（已剥离开头指令词）` 一行即为剥离判定的观测点；未打印
该行表示保留了原查询。真实链路需配置 `SILICONFLOW_API_KEY`，并复用 `~/.lucia/code-context/`
下的按仓库向量缓存，否则每轮都会重新嵌入全仓库。

指标为本机与当次端点的结果，不作为跨环境 SLA；查询集偏向 uni-app 业务前端，不能代表后端或
其他技术栈的检索准确率。

## 八、2026-09-06：复核召回归因，短函数独立向量实验不合入

**结论：恢复短函数独立向量的完整 A/B 未通过真实检索准确率验收，改动已回退。**
机械 Precision@10 显著提高，但 Recall 与 MRR 不显著；逐项核对源码后，增量还混入了
已覆盖正文的具名化、语义假朋友和占位函数。不能将这些计数变化报告为准确率显著提升。
本节补充并纠正第六节的归因，保留前面各节作为当时的实验记录。

### 已核实的失败机制

Vue 原有的全页语义窗口被 AST 子区间替代后，部分调用者与被调用函数不再共享检索语境。
例如视频互动的两个原子声明及其向量都仍存在，原短函数组 ID 也未改变；但旧窗口同时覆盖
触发判断和暂停播放，新块没有联合覆盖这两段。食谱创建函数同样仍正确解析并拥有独立向量，
其旧窗口包含邻近的提交、取消及确认语境，拆细后 Top-10 未返回完整创建实现。

这证明了索引表示发生变化，不能进一步声称“目标没有进 150 候选”或“被上下文配额剔除”：
本轮真实结果日志没有保存内部候选阶段，不能重犯只看最终列表就推断召回阶段的错误。
